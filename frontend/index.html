1. Core: how it works

The core is the protocol a browser and a server speak over a WebSocket, called ksock. Its notifications are carried in three layers, each inside the one below it:

  1. The WebSocket carries binary messages only.
  2. Each WebSocket message is one BSON document.
  3. Each BSON document is a JSON-RPC 2.0 notification: hello, grant, heartbeat or message.

On these layers, ksock adds what the WebSocket API of browsers lacks: flow control, with grants, and the detection of a lost connection within seconds, with heartbeats.

The protocol is symmetric. The browser and the server follow the same rules, so this section calls both of them endpoints.

The key words MUST, MUST NOT, SHOULD and MAY are to be interpreted as described in RFC 2119.

1.1 Messages on the wire

An endpoint MUST send binary WebSocket messages only. Each WebSocket message MUST contain exactly one BSON document, with nothing before or after it.

Each document MUST be a JSON-RPC 2.0 notification: it has the member jsonrpc with the value "2.0", the member method with the name of the notification and, if the notification has parameters, the member params with them by name. It has no id, as nothing is answered on this layer.

Counts, sizes and times are integers. BSON libraries encode numbers differently, small ones as int32 and large ones as int64 or double, so an endpoint MUST accept any BSON number type that holds an integer.

Notification Parameters Purpose
hello protocol, version, heartbeatTimeout names the protocol and its version, sent first (1.2)
grant messages, bytes allows the other endpoint to send (1.3)
heartbeat none shows that the connection is alive while nothing else is sent (1.4)
message data carries a message of the application (1.5)

The examples in this section show BSON documents in JSON notation, with binary data as <binary …>.

1.2 Opening a connection

As soon as the WebSocket is open, each endpoint sends its hello and then its first grant, without waiting for the other endpoint. The hello tells the other endpoint that it is talking to an endpoint of this protocol, and in which version.

Parameter Type Value
protocol string "ksock"
version integer the version of the protocol, 1 for this specification
heartbeatTimeout integer the longest time in milliseconds the endpoint waits for a notification of the other endpoint, greater than 0 (1.4) 
{
  "jsonrpc": "2.0",
  "method": "hello",
  "params": { "protocol": "ksock", "version": 1, "heartbeatTimeout": 10000 }
}
  • The first notification an endpoint receives MUST be a hello with the protocol "ksock". Anything else is a protocol violation.
  • An endpoint that does not implement the version of the other endpoint MUST close the connection.
  • An endpoint sends its hello once. A second one is a protocol violation.

1.3 Flow control with grants

A browser cannot apply backpressure to a WebSocket. The WebSocket API hands every message to the page as soon as it arrives, with no way to pause receiving, and send() buffers whatever it is given. An endpoint that sends faster than the other one processes fills the memory of the other one. ksock therefore controls the flow on its own layer: an endpoint only sends the message notifications that the other endpoint allowed with a grant.

Parameter Type Value
messages integer how many message notifications the other endpoint may send
bytes integer how many bytes these may take together 
{
  "jsonrpc": "2.0",
  "method": "grant",
  "params": { "messages": 16, "bytes": 65536 }
}

Sending under a grant

  • An endpoint keeps a credit of messages and bytes. It starts at 0 messages and 0 bytes, so no endpoint sends a message notification before it received a grant.
  • A received grant sets the credit to its messages and bytes. It does not add to what is left of the credit: the last grant received counts, from then on until the next one.
  • Every message notification sent takes 1 message and its size in bytes from the credit. Its size is the length of its BSON document, which is the length of the WebSocket message, including the bytes of the notification around the data.
  • An endpoint MUST NOT send a message notification that its credit does not cover, in messages and in bytes. It waits for the next grant instead. message notifications go out in the order the application sends them, so one that waits holds back the ones after it.
  • Only message notifications take from the credit. hello, grant and heartbeat are sent whatever the credit is, so an endpoint without credit still grants and sends heartbeats.

Granting

  • Each endpoint sends its first grant right after its hello.
  • After that, an endpoint MUST NOT send its next grant before the message notifications it received since its last one used up half of that grant's messages or half of its bytes, whichever comes first. This keeps grants, which no grant limits, from flooding the connection. It has to be whichever comes first: a grant of many bytes for few messages would otherwise never be followed by another once its messages are used up.
  • An endpoint grants when it is ready for more, e.g. once its application has processed the messages it received. This is what makes grants backpressure: the other endpoint only sends as much as it was granted.
  • An endpoint SHOULD grant at least as many bytes as the largest message it accepts, as a message larger than the credit can never be sent.

A grant replaces the credit instead of adding to it. So the message notifications the other endpoint sent before the grant reached it were sent under the grant before, and an endpoint can receive more after sending a grant than that grant allows.

1.4 Heartbeats

TCP notices a lost connection late: while nothing is sent, not at all, and while data is sent, only once its retransmissions have given up, which takes minutes. WebSocket has ping and pong frames for this, but browsers neither let a page send a ping nor tell it about a pong. ksock therefore detects a lost connection with its own notifications, within a time each endpoint chooses.

  • Each endpoint announces in its hello its heartbeatTimeout: the longest time it waits for a notification of the other endpoint. The two endpoints can announce different times, but both announce one, so there are heartbeats in both directions.
  • Every notification is a sign of life: a hello, grant or message that an endpoint sends or receives counts as a heartbeat.
  • An endpoint sends a heartbeat only when it has sent nothing else for a while. It MUST send one before the heartbeatTimeout of the other endpoint passes without a notification from it, and it SHOULD send one once it has sent nothing for half of that time, which leaves the other half for the heartbeat to arrive, for timeouts in the range of seconds.
  • An endpoint that receives no notification within its own heartbeatTimeout MUST close the connection. The time runs from the opening of the WebSocket, so the hello of the other endpoint has to arrive within it too.
  • Until the hello of the other endpoint arrives, an endpoint does not know its heartbeatTimeout. Its own hello and first grant, sent right at the start, are its first signs of life.

A heartbeat has no parameters:

{
  "jsonrpc": "2.0",
  "method": "heartbeat"
}

1.5 Messages of the application

A message notification carries one message of the application, as it is, in binary data. This layer does not look into it. Section 3 recommends what applications put in it.

Parameter Type Value
data binary the message of the application, as BSON binary data of the generic subtype 0 
{
  "jsonrpc": "2.0",
  "method": "message",
  "params": { "data": <binary 68 65 6c 6c 6f> }
}

1.6 Closing the connection

Either endpoint can close the connection at any time, normally with the close code 1000. An endpoint that closes the connection because of the other endpoint uses one of these close codes:

Code Reason When
4000 protocol violation a text message, a WebSocket message that is not one BSON document, a document that is not one of the notifications of this section with its parameters, a first notification that is not a hello of ksock, a second hello
4001 unsupported version the hello names a version the endpoint does not implement
4002 heartbeat timeout no notification arrived within the heartbeatTimeout

The codes are from the range 4000 to 4999, which WebSocket leaves for private use. Browsers only close a WebSocket with 1000 or a code from 3000 to 4999, so the codes WebSocket defines for these cases, 1002 for a protocol error and 1003 for data that cannot be accepted, are not available to the browser.

After a heartbeat timeout, the other endpoint will most likely not answer the close. An endpoint considers the connection closed right away, without waiting for the closing handshake to finish.

2. Recommended libraries

The core does not prescribe an implementation. For its layers, these libraries are recommended. Both run in browsers and in Node.js, so the browser and the server can share the code of their endpoints.

Layer Library
BSON documents bson
JSON-RPC 2.0 notifications @k13engineering/yajrpc

2.1 bson

bson is the default BSON package on npm, maintained by MongoDB. It turns a notification into the bytes of a WebSocket message and back:

  • serialize() encodes a notification as a BSON document, the bytes to send as a binary WebSocket message.
  • deserialize() decodes the bytes of a received WebSocket message into its notification.
  • Binary holds the data of a message notification. Its default subtype is the generic subtype 0 the core requires.
  • calculateObjectSize() gives the size of the BSON document of a notification before it is encoded, which is what a message notification takes from the credit (1.3).

2.2 @k13engineering/yajrpc

@k13engineering/yajrpc implements JSON-RPC 2.0 for both ends of a connection: requests, notifications and responses.

  • Its core, createJrpc(), does not depend on a transport. It hands out the messages to send and takes in the ones received, so it combines with bson and with the grants and heartbeats of ksock.
  • createRpcNotificationsDefinition() defines notifications with a parser for their parameters. An endpoint then handles hello, grant, heartbeat and message only with valid parameters, and learns of any other notification as unknown or invalid, which the core treats as a protocol violation (1.6).
  • createRpcRequestsDefinition() does the same for requests.

A type-safe definition with createCombined

It is recommended to define a protocol once, with createCombined(), from the requests and notifications that each of its two sides handles. Each endpoint takes its side of the definition and gets from it the handlers of what it receives and the methods for what it sends. TypeScript checks the parameters of both, and the parsers check what actually arrives.

For the core, the two sides are the same, as ksock is symmetric:

import { Binary } from "bson";
import {
  createCombined,
  createRpcNotificationsDefinition,
  createRpcRequestsDefinition,
  type TObjectParser
} from "@k13engineering/yajrpc";

type THello = { protocol: "ksock", version: number, heartbeatTimeout: number };
type TGrant = { messages: number, bytes: number };
type TMessage = { data: Binary };

const isRecord = (raw: unknown): raw is Record<string, unknown> => {
  return typeof raw === "object" && raw !== null && !Array.isArray(raw);
};

// bson reads int32, int64 and double as numbers
const isCount = (value: unknown): value is number => {
  return Number.isSafeInteger(value) && (value as number) >= 0;
};

const isHello = (raw: unknown): raw is THello => {
  return isRecord(raw) && raw.protocol === "ksock" && isCount(raw.version) &&
    isCount(raw.heartbeatTimeout) && raw.heartbeatTimeout > 0;
};

const isGrant = (raw: unknown): raw is TGrant => {
  return isRecord(raw) && isCount(raw.messages) && isCount(raw.bytes);
};

const isMessage = (raw: unknown): raw is TMessage => {
  return isRecord(raw) && raw.data instanceof Binary &&
    raw.data.sub_type === Binary.SUBTYPE_DEFAULT;
};

// takes the parameters as they are, if they are valid
const createParser = <T>(
  isValid: (raw: unknown) => raw is T
): TObjectParser<T> => {
  return {
    parse: ({ raw }) => {
      return isValid(raw)
        ? { error: undefined, value: raw }
        : { error: Error("invalid parameters"), value: undefined };
    },
    format: ({ value }) => {
      return value;
    }
  };
};

// for a notification without parameters, whose params are left out
const noParamsParser: TObjectParser<void> = {
  parse: ({ raw }) => {
    return raw === undefined
      ? { error: undefined, value: undefined }
      : { error: Error("unexpected parameters"), value: undefined };
  },
  format: () => {
    return undefined;
  }
};

// ksock is symmetric: both endpoints handle the same notifications,
// and neither has requests
const ksockEndpoint = {
  requests: createRpcRequestsDefinition({}),
  notifications: createRpcNotificationsDefinition({
    hello: { paramsParser: createParser(isHello) },
    grant: { paramsParser: createParser(isGrant) },
    heartbeat: { paramsParser: noParamsParser },
    message: { paramsParser: createParser(isMessage) }
  })
};

const ksockProtocol = createCombined({
  sideADefinitions: ksockEndpoint,
  sideBDefinitions: ksockEndpoint
});

noParamsParser formats the parameters of a heartbeat as undefined, a member bson leaves out, so a heartbeat goes out without params as the core requires (1.4).

An endpoint, e.g. the server on side A and the browser on side B, then handles and sends typed notifications:

const server = ksockProtocol.sideA({
  incomingNotifications: {
    notifications: {
      hello: ({ version, heartbeatTimeout }) => { … },
      grant: ({ messages, bytes }) => { … },
      heartbeat: () => { … },
      message: ({ data }) => { … }
    },
    // protocol violations (1.6)
    handleUnknownNotification: () => { … },
    handleParametersParseError: () => { … }
  },
  incomingRequests: { … },
  // notify and request of createJrpc()
  outgoingNotify: …,
  outgoingRequest: …
});

server.outgoingNotifications.grant({ messages: 64, bytes: 1048576 });

The same works for the protocol of an application, whose two sides usually handle different requests and notifications.
